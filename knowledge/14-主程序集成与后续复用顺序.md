# 主程序集成与后续复用顺序

## 目标

以 `main@fab5509` 为唯一开发起点，小批恢复功能并保持问题可归因。当前基线包含核心运行时和 UI Shell，但系统面板上滑返回仍需先修复；旧计划 3～6 只能提供设计思路或少量人工移植参考。

## 推荐边界

- UI 主循环是唯一 LVGL 所有者；后台通过固定命令、事件和快照通信。
- 触摸、RTC、PMU、IMU 共享一个 I²C 所有者。
- SD、音频、Wi-Fi、传输和 OTA 使用显式租约与功耗门控。
- 每个阶段分别保存自动证据和真机记录；未执行的硬件项保持未验证。
- 问题修在最早责任模块，不把补丁堆到总装层。
- 未经明确授权不提交、合并、推送或创建发布标签。

## 最小实现

1. **稳定 UI（计划 2/2A）。** 修复面板完整手势接收，反复验证锁屏、桌面、下拉、上滑、BOOT 和息屏。
2. **统一硬件总线与电源（计划 3）。** 先触摸，再 RTC、PMU、IMU；每加入一个设备就做长时间触摸和唤醒回归。
3. **收敛时间与核心应用（计划 3）。** 从现有 RTC/闹钟装配开始，先用单闹钟闭环验证服务边界，再迁移固定槽位、设置和工具。
4. **建立 SD 与音频闭环（计划 4）。** 先 NVS、FFat 和 SD 受管入口，再播放、录音和主题；分别验证拔卡、冲突、收尾和功耗。
5. **开发 BLE（计划 5）。** 从 Hello、Pair、Ack 开始，真机稳定后再加入通知和设置。
6. **开发 Wi-Fi 与天气（计划 6）。** 先 NTP，再认证配网、手机天气和直连天气，逐项验证断网与低电。
7. **开发传输与 OTA（计划 6）。** 先受管临时文件，再签名双应用分区 OTA、首启回滚和 Release 闭锁。
8. 任一阶段失败时回到最近的真机稳定点，修复并复测后再继续。

## 主要风险

一次性回灌旧总装会同时引入跨核 I²C、密集轮询、资源冲突和无法归因的真机故障。当前分区表或 UI 占位存在，不表示对应 OTA、无线或应用功能已经实现。编译、Python 测试和 APK 只属于自动证据。
