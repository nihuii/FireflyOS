## 1. 目标

从计划 1～6 的最终软件分支中提炼可供 FireflyOS 重启开发参考的模块知识，并保存到当前 `main` 的 `knowledge` 目录。知识库面向后续开发者和自动化代理，要求无需保留 `wifi-weather-ota` 工作树也能理解模块边界、定位原始实现并从 Git 精确取回源码。

知识库不是新基线代码，也不代表计划 1～6 已通过真机验收。自动测试、固件编译和 Android Debug 构建只能作为软件证据；正式真机项目保持 `PENDING`。

## 2. 非目标

- 不把计划 3～6 重新合并到 `main`。
- 不复制完整源码树、构建产物或生成缓存。
- 不复制测试私钥正文、临时服务器日志或本机路径日志。
- 不修改当前固件、Android 应用或测试代码。
- 不把已发现问题的实现描述为可直接复用。
- 不提交、不推送、不删除工作树。

## 3. 来源与可追溯性

所有代码结论以提交 `e4fb0d1ff71bcc0330b507fa90c653be9929e611` 为准。每个模块文档必须记录：

1. 来源分支和完整提交哈希。
2. 原始文件路径与关键符号名称。
3. 精选代码片段对应的来源路径。
4. 使用 `git show e4fb0d1:<path>` 取回原文件的命令。
5. 对应自动测试、设计文档和模块说明。

路径引用不得依赖 `.worktrees/wifi-weather-ota` 的长期存在。必要时可使用当前工作树进行读取，但知识库中的永久定位必须使用 Git 提交和仓库相对路径。

每个编号模块使用相同章节：

5. 数据流、线程归属、LVGL 边界和硬件访问边界。

8. 软件验证证据与仍为 `PENDING` 的真机项目。
9. 已知问题、反例和复用注意事项。
10. 基于 `main@351dff7` 的最小引入步骤。

## 6. 复用等级

### 可直接参考

模块边界清晰，固定容量和失败路径明确，且具备对应自动测试。该等级只表示设计和代码结构可供参考，不等于真机功能通过。

### 需要重构后复用

核心思路有价值，但依赖后续计划、共享硬件总线、跨核状态或大型入口文件。必须切小后重新测试和真机验收。

### 仅作反例或诊断参考

已经发现明确缺陷，或者实现违反当前重启原则。文档必须说明故障机制和替代约束，禁止直接复制进入新基线。

## 7. 必须显式记录的风险

- UI Shell 下拉面板的大部分子控件会拦截手势，导致面板无法稳定上滑返回。
- 计划 3 中触摸读取与 PMU、RTC、QMI8658 共用 `Wire`，但触摸侧绕过共享 I²C 锁；后台轮询可能与 UI 核触摸读取并发。
- BOOT 键进入一瞥后自动黑屏符合原有两秒状态转换，不能单凭该现象判断固件崩溃。
- 烧录中途的 pySerial `PermissionError` 属于主机 USB、驱动、端口占用或下载链路问题，不能归因于正在上传的应用逻辑。
- 计划 1～6 正式真机验收项均不得由自动编译或单元测试代替。
- Release 缺少仓库外生产公钥时按设计失败闭锁，不得在知识库中伪造发布产物或生产密钥。

## 8. 精选代码规则

- 每段通常控制在 10～60 行；超出时拆分为接口和关键实现两段。
- 保留原始类型名和方法名，不为了文档展示而改写实现。
- 省略无关代码时使用文字说明，不使用会被误认为可编译代码的伪实现。
- 代码块前标注来源提交、路径和符号。
- 对跨文件流程同时给出调用顺序，避免孤立片段造成错误理解。
- 测试私钥只说明用途和路径，不展示 PEM 内容。

## 9. 校验方式

`validate_knowledge.py` 只检查知识库一致性，不执行固件或 Android 构建。它应验证：

- 设计列出的模块文档全部存在。
- 模块文档包含来源提交、复用等级、源码映射、验证边界和复用步骤。
- 所有 `e4fb0d1:<path>` 引用可通过 `git cat-file -e` 定位。
- 知识库内部 Markdown 链接指向存在的文件。
- 不存在占位符或未完成标记。
- 不包含 PEM 私钥正文、常见令牌格式和 `.worktrees` 永久路径依赖。

校验通过只证明知识库结构和引用一致，不证明功能或硬件通过。

## 10. 实施顺序

1. 建立总索引和源码取回说明。
2. 按功能域提取类、接口、状态机和关键实现。
3. 为每个模块补齐测试、文档、风险和复用步骤。
4. 汇总主程序集成顺序，建立从 `main@351dff7` 重新引入功能的建议路径。
5. 编写校验脚本并执行一致性检查。
6. 检查 Git 状态，确认只新增 `knowledge` 内容。
