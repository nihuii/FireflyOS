## 复用等级

**可直接参考边界与状态机，硬件适配需重写。** 固定容量诊断、能力快照、两阶段恢复确认、受管清除白名单和 Release 失败闭锁适合尽早恢复；旧主程序中的所有 owner 适配和暂停任务逻辑只作参考。

## 模块定位

诊断服务提供不依赖云端的有界运行记录；硬件能力服务区分“未探测、不可用、降级”和具体失败原因；恢复出厂服务只清除明确登记的数据所有者，并把 SD 清除作为第二次独立确认。构建脚本保证缺少仓库外生产材料时不能生成 Release。

## 职责与边界

- `DiagnosticService`：采集堆、PSRAM、任务栈、事件丢弃、功耗模式和重启原因，保留最近 64 条。
- `SerialDiagnosticExport` / `SdDiagnosticExport`：显式导出，不在正常循环中持续写 SD。
- `HardwareCapabilities`：为 RTC、PMU、IMU、SD、Codec、BLE、Wi-Fi 保存可用性和失败原因。
- `FactoryResetService`：预览、内部确认、可选 SD 二次确认、执行、失败和重启。
- `FactoryResetOwners`：各数据所有者自己实现清理；服务不猜测路径。
- 构建/发布脚本：区分 Development 与 Release，校验生产输入、分区和镜像大小。

恢复出厂不是“格式化所有介质”。默认清理 pairing、Wi-Fi、通知、天气、设置和缓存；只有用户再次确认时才清理 FireflyOS 受管 SD 根目录，绝不扩大到整张卡或用户未受管文件。

## 数据流与线程边界

```text
运行指标 -> 周期/会话边界采样 -> 64 条环形记录 -> 串口或 SD 显式导出

用户发起恢复 -> Preview(generation)
                    |
             确认内部清除
                    |-- 不清 SD --> 执行 owners -> reboot
                    |
             二次确认清 SD --> 仅受管根目录 -> reboot

Release 构建 -> 检查仓库外公钥 + HTTPS 配置 -> 分区/镜像校验 -> 产物
                 任一缺失或越界 --------------------------> 失败，无发布产物
```

执行恢复时旧实现暂停后台 worker，并在临界区之外调用 owners，避免持锁执行文件和 NVS I/O。新实现也应先冻结新业务、等待资源租约收敛，再按 owner 顺序清理。

## 关键接口

| 项目 | 固定边界 |
|---|---:|
| 诊断记录 | 64 条环形容量 |
| 周期采样 | 60 s |
| 单条诊断记录 | 不超过 40 B |
| 能力项 | RTC、PMU、IMU、SD、Codec、BLE、Wi-Fi |
| 能力快照 | 14 B |
| 恢复确认 | generation + 内部确认 + 可选 SD 二次确认 |
| Release 生产输入 | 本地公钥头 + 本地 HTTPS 配置头，均不跟踪 |

## 验证边界

自动测试可证明容量、状态迁移、确认 generation、owner 调用顺序和构建闭锁；不能证明真实堆水位、任务栈安全余量、SD 导出、断电中的恢复、清理后的首启或任何真机功能。Release 按设计失败不能写成发布成功。计划 1～6 正式真机项仍为 `PENDING`。

## 已知问题

- 诊断采集若在热路径打印或频繁写卡，会反过来改变时序和故障表现；常态只写 RAM 环形缓冲。
- 事件丢弃计数必须与事件总线同源，不能在 UI 层估算。
- 工厂恢复失败后要保留可诊断状态，不能无条件重启并掩盖部分清理。
- 清 SD 必须由受管路径白名单实现；禁止递归删除盘符根目录或模糊匹配路径。
- 生产公钥用于验签，不是私钥；即便如此也必须由正式发布流程提供，不能拿测试公钥顶替。

## 基于 main 的复用步骤

1. 最先引入硬件能力快照和 64 条 RAM 诊断环，不接 SD 导出。
2. 为每个已真机验证的驱动登记探测结果和失败原因，并记录事件丢弃/栈水位。
3. 建立数据所有权清单和受管 SD 根目录，逐个 owner 写幂等清理测试。
4. 接入恢复预览、generation、内部确认；真机验证后再加入 SD 二次确认。
5. 增加串口/SD 手动导出，验证导出失败不破坏环形记录和正常服务。
6. OTA 恢复时再启用 Release 生产输入、分区和尺寸闭锁，继续保持缺配置即无产物。
