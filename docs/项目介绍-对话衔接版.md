# FireflyOS 项目介绍与当前开发衔接

## 1. 项目定位

FireflyOS 是 ESP32-S3-Touch-AMOLED-2.06 的本地优先、独立运行的腕端系统。
目标是在受限硬件上建立可维护体验，不能将枚举、路由或分区预留误称为完整服务。
设备采用 410×502 圆角 AMOLED，交互、排版和预览均以实际分辨率为准。

当前重点是核心交互、硬件稳定性和可调试性，再逐步扩展能力。
新增功能应先定义运行位置、状态来源、资源上限与真机验证方式。
交接内容只陈述当前可核验事实与明确边界。

## 2. 硬件与构建环境

目标板为 ESP32-S3-Touch-AMOLED-2.06，屏幕/触控为 CO5300/FT3168。
板载器件包括 PCF85063 RTC、AXP2101 PMU、QMI8658 IMU、ES8311 和 SD_MMC。
图形库只能使用 LVGL 8.3.11；不得混用 LVGL 9 的 API、示例或迁移规则。

仓库根目录也是 Arduino Sketchbook：`D:\Study\Projects\ESP32Projects\FireflyOS`。
Arduino IDE 以 `Firefly\Firefly.ino` 作为工程入口。
`docs/Arduino-IDE配置指南.md` 只用于当前 Arduino 板卡、构建和 Sketchbook 设置；其旧 worktree/计划状态段落应忽略，以本交接和当前 Git 证据为准。
当前 32MB 分区中，app0 偏移 `0x10000`、大小 `0x480000`。
app1 偏移 `0x490000`、大小 `0x480000`；otadata 偏移 `0xe000`、大小 `0x2000`。
FFat 偏移 `0x910000`、大小 `0x16E0000`；coredump 偏移 `0x1FF0000`、大小 `0x10000`。

`build_opt.h` 将 Arduino 任务和事件任务置于 core 0。
双应用分区只表示布局具备条件，不代表已经存在 OTA 服务、更新协调器或启动校验流程。
修改分区或构建参数前，先记录并验证现有偏移、容量和启动行为。

## 4. 当前仓库结构

`Firefly/` 是 Arduino 主程序和嵌入式实现入口，构建从 `Firefly\Firefly.ino` 开始。
`docs/` 保存系统架构、构建说明、模块说明和当前交接资料。
`knowledge/` 保存历史设计提炼、源码取回线索与复用顺序，不是功能已经落地的证明。

`libraries/` 容纳本地库与依赖素材，应以现有构建结果处理依赖变动。
`image/图片生成提示词` 是受保护的素材目录。
测试和工具支持回归、资源和开发辅助；通过它们不替代真机验收。
查找模块时从当前入口和引用关系开始，不能根据历史目录名判断服务存在。

## 5. 当前 main 已有能力

当前 main 已实现核心事件、状态、生命周期、应用、资源和能力原语。
RTC、PMU 与 HAL 已有锁管理路径和板级适配器，构成现有硬件访问基础。
`Firefly/touch.h` 的 TouchLib 仍直接访问 `Wire`，尚未纳入通用 I2C 所有权。
已实现 UI Shell、导航、主题和通用组件。

已实现锁屏、主页、一瞥、控制中心、通知和系统覆盖层等界面与交互基础。
已具备电池/充电行为、RTC 读写、闹钟调度、闹钟 UI 和闹钟持久化。
已包含 `Qmi8658ControlAdapter`，以及相应的测试与工具支撑。

Activity、Weather、Music、Recorder、Files 目前只是 UI 路由或占位。
没有独立实现和验证材料时，不要将这些界面称为已实现应用。
以下后续服务仍缺失：Android 伴侣目录、BLE 传输/服务、Wi-Fi/天气服务。
存储/媒体引擎、大文件传输、OTA 更新协调器和启动校验服务同样缺失。
核心枚举、路由和分区支持都不是这些服务的实现证据。

评估“已实现”至少需要源码路径、可调用入口、回归验证和真机边界的相应证据。
评估“占位”时应清楚区分界面可见性与功能可用性。

## 7. 不可破坏的约束

所有 LVGL 访问只能发生在 UI 主循环中。
后台服务不得调用 LVGL，只能通过受控事件或状态边界请求 UI 更新。
UI 必须遵守 410×502 安全区，触摸目标至少 48px。

正式 UI 改动先做预览，再进入设备验证和合并判断。
资源、队列和缓存必须采用固定容量，避免长期运行时无界增长。
功能设计坚持本地/独立运行优先，联网和伴侣能力只能是后续扩展。

目标约束是触控、RTC、PMU 与 IMU 共享一个 I2C 所有权边界，访问路径可序列化、可诊断；当前尚未完全达到。
新增并发或后台 I2C 工作前，必须先将 Touch 纳入同一边界；后台设备不得绕开该边界。
跨线程通信不得泄露显示对象、驱动句柄或 I2C 会话。
输入命中、手势传播和页面切换属于 UI 主循环统一设计范围，需要整体回归。
自动测试、构建成功和预览通过都不是硬件验收，仍须在目标板验证。

保护 `image/图片生成提示词`；未经授权不得删除、恢复、提交、合并、推送或打 tag。
影响供电、总线或启动的变更必须有可观察日志和明确的回退判断。

## 8. 本轮交付范围与已知问题

本轮对齐范围包括 19 个 knowledge 文件、9 份 `docs/执行计划` 和本交接文档的改写。
还包括 5 份新增的 superpowers 规格/计划文档，以及知识库校验器的回归测试。
一并保留的删除是 `docs/真机验证与分支同步流程.md`、`docs/项目介绍.md` 和 `libraries/TouchLib-main.zip`。

这些内容应作为同一轮基线对齐整体审查和交付；未经新的明确授权不得恢复其中的删除。
系统面板的软件修复已在当前源码加入完整事件冒泡、方向仲裁和控件保护；自动契约与构建已通过，但目标板 20 次分类矩阵尚未执行，不能写成完整 Gate B 已关闭。
BOOT、一瞥（Glance）或屏幕熄灭必须用日志和硬件现象与崩溃严格区分，不能凭屏幕表象判断。

添加后台设备前必须先将 Touch 纳入共享 I2C 所有权，否则触控、时钟、电源和 IMU 的并发访问会失稳。
ROM/stub 上传期间的 pySerial `PermissionError` 是应用执行前的上传链路排查：先检查 COM 端口占用/串口监视器、驱动和 USB 断连。
线缆、电源、stub 与波特率是更广义的上传因素，不能据此声称波特率本身导致操作系统权限拒绝。
排查先记录复现条件、串口日志和最小验证，不能把传输层问题误归因于应用逻辑。

在脏工作区中，先区分本次改动与预先存在的用户改动。
不要用大范围格式化、恢复命令或依赖升级掩盖单一交互或硬件问题。
最终交付前检查完整 diff，避免把知识库改写、删除项和功能改动混为一组提交。
