# FireflyOS 低功耗唤醒矩阵

## 当前结论

截至 2026-07-03，FireflyOS **未启用真实 LightSleep**。当前发布默认仍是 `ScreenOff` 状态下将显示亮度设为 0，CPU 与 UI 主循环继续运行。

原因不是软件生命周期接口缺失，而是 BOOT、PWR、RTC 闹钟等必需唤醒源尚未完成每项 100 次真机验证，且板级 `FIREFLY_PWR_WAKE_GPIO` / `FIREFLY_RTC_WAKE_GPIO` 尚未在真机确认后定义。`PowerService::canEnterLightSleep()` 已将 BOOT、PWR 和 RTC 闹钟固定为必需项；任一项少于 100 次，或存在一次失败，都会在准备资源前返回 `GateClosed`。

## 当前软件生命周期

`PowerService::attemptLightSleep()` 已实现固定顺序：检查 100/100 门禁、调用 `prepare()`、调用平台睡眠入口、无论入口成功或失败都调用 `restore()`。该调用只存在于 UI 主循环路径；后台任务不调用 ESP 睡眠 API 或 LVGL。

当前 `prepare()` 会保存运动汇总、关闭屏幕手电筒、暂停后台任务、把 QMI8658 切到低功耗配置并将屏幕亮度设为 0。当前 `restore()` 会恢复 QMI8658 正常配置、恢复后台任务和必要的显示状态；IMU 恢复失败时会关闭 Motion 能力，避免继续使用失效设备。

由于当前音频、SD、Wi-Fi/BLE 会话尚未在主系统启用，本阶段没有伪造这些模块的停机/恢复逻辑。它们将来接入后必须扩展同一生命周期。

## 完整产品睡前与恢复顺序

真实 LightSleep 启用前，必须按以下顺序完成并真机验证：

1. UI 主循环停止面板动画并关闭系统覆盖层。
2. 停止音频与 SD 会话；刷新需要持久化的闹钟、活动和设置状态。
3. 停止 Wi-Fi/BLE 高功耗会话，保持 RTC、PMU 与已验证的唤醒源供电。
4. 关闭显示背光/面板输出，配置通过 100/100 门槛的唤醒源。
5. `PowerService::attemptLightSleep()` 的准备钩子成功后，才允许调用 ESP32 LightSleep。
6. 唤醒后先恢复共享 I2C、PMU、RTC、显示和触摸，再恢复当前 Shell 路由。
7. 最后恢复网络、音频等增强模块，并由恢复钩子完成生命周期。

`SleepHooks` 使用固定函数指针，不分配动态内存。钩子只能由 UI 主循环发起；后台任务仍然只投递事件，不调用 LVGL。

## 启用门槛

- BOOT：100/100 成功，且无双触发或漏触发。
- PWR：短按、长按及快速抖动均完成计划中的计次测试；作为唤醒源时 100/100 成功。
- RTC 闹钟：100/100 成功，跨日闹钟也能唤醒。
- 任一必需源失败后立即保持当前亮度归零黑屏方案，不进入 LightSleep。
- IMU 只有达到抬腕成功率不低于 95%，且 30 分钟静置误唤醒不超过 1 次，才可加入唤醒矩阵。
- ScreenOff 但 CPU 未睡眠时保持 QMI8658 正常陀螺仪配置；不得为了省电提前关闭抬腕判定所需的陀螺仪。
