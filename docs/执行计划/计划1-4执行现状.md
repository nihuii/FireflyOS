## 1. 判定口径

本文区分以下四种状态：

1. **软件已实现**：计划要求的类、服务、应用和正式固件运行接线已经存在。
2. **自动验证通过**：Python 契约测试、固件编译和文档检查已经通过。
3. **视觉验收通过**：预览已由用户完成最终复核，且与真机显示对照无明显偏差。
4. **真机验收通过**：按执行计划规定的次数和场景在开发板上完成验证。

自动测试和 Arduino 编译不能代替视觉或真机验收。原始计划 01～04 的复选框大多没有随提交逐项回填，因此本文以实际代码、Git 历史、补全计划、模块说明和验收记录为主要证据。

## 4. 计划 1：工程基线与模块化核心

### 4.1 已实现

- 可复现的 Arduino CLI 构建脚本、统一验证脚本和 Python 契约测试入口。
- 固件、内存、启动时间和运行诊断的基线采集格式与解析工具。
- FireflyOS 本地 Arduino 库骨架和聚合头文件。
- 固定容量 `EventBus`，包含关键事件策略和拒绝计数。
- `StateStore`、`CapabilityRegistry`、静态 `AppRegistry`。
- `SystemLifecycle`、`AppManager`、`ResourceGovernor` 和 OTA 联合准入。
- `I2cBusManager`、`LegacyBoardAdapter`、`LockedRegisterDevice`。
- RTC、PMU 和寄存器设备的共享 I2C 超时互斥边界。
- 后台任务只投递事件，Arduino UI 主循环消费事件并执行 LVGL 操作。
- Gate A 的串口诊断输出，包括内存低水位、事件拒绝数和桌面转场最大耗时。

### 4.2 尚未完成

- 锁屏、桌面、设置、双闹钟、电池和亮度与迁移前基线的真机对照。
- BOOT 短按 30 次、息屏/唤醒 10 次、自动息屏 5 次压力测试。
- 内部 SRAM 最低余量不低于基线 85% 的真机数据。
- 锁屏进入桌面最大耗时不比基线增加 15% 以上的真机数据。

结论：计划 1 的软件功能已经进入 `main`，但 Gate A 尚未关闭。

## 6. 计划 3：核心应用、电源与 IMU

### 6.1 已实现

- `TimeService` 与双槽 `AlarmService`，支持跨日、重复规则和同分钟去重。
- Clock 应用的双闹钟、倒计时和秒表；离开页面后继续计时。
- Settings 应用的固定容量命令队列，硬件操作回到 UI 主循环执行。
- 42 格日历、8 条摘要缓存、24 字符计算器和最长 60 秒屏幕手电筒。
- `PowerService` 电源状态机和 BOOT/PWR 统一输入语义。
- LightSleep 准备、进入、恢复、失败回滚和 UI 主循环门禁链路。
- `Qmi8658Device`、32 样本 `MotionService` 环形缓冲、计步、抬腕和活动应用。
- 活动汇总每 15 分钟或息屏前持久化，不保存全天原始 IMU 数据。
- 活动页面不显示心率、血氧、睡眠或其他不存在的医疗数据。

### 6.2 尚未完成或未启用

- 真实 `esp_light_sleep_start()` 发布配置未启用。BOOT、PWR、RTC 等必需唤醒源仍为 0/100，门禁保持关闭。
- RTC 无效状态、手动设置和恢复待真机复测。
- 双闹钟、倒计时离开页面触发和 BOOT/PWR 计次待真机。
- QMI8658 WHO_AM_I、10 分钟静置误计步和 I2C 稳定性待真机。
- 100 次抬腕、30 分钟静置误唤醒和至少 3000 步参考设备对比未执行。
- Active、IdleDim、ScreenOff、LightSleep 电流及 400mAh 阶段续航未测量。

结论：计划 3 的软件结构和运行接线已经完成，但真实 LightSleep 尚未交付，传感器精度、唤醒可靠性和续航尚未验收。

## 7. 计划 4：存储、音频与媒体应用

### 7.1 已实现

- 四个版本化 NVS 命名空间、旧 Preferences 迁移和 LittleFS 非格式化恢复。
- `StorageService` 作为媒体业务唯一受管 SD 入口，提供受锁的 open/read/write/seek/close/exists/remove/rename/openNext。
- SD_MMC 1-bit 引脚与 `/FireflyOS/` 七个受管目录，拒绝路径逃逸。
- 应用 I/O 结果传播到 `SdCardDevice`，连续两次失败进入 `SdRemoved` 流程。
- `Es8311Device`、I2S、功放低功耗和 `Alarm > Recorder > System > Music` 音频会话优先级。
- PCM/WAV 流式播放、录音、WAV 头回填和临时录音清理。
- 四个固定索引的内置闹钟铃声和 `AlarmTriggered` 事件链。
- Files、Music、Recorder、Themes 四个真实应用页面及桌面路由。
- Files 后台分页：固定 32 项、48 字节名称、每轮最多扫描 4 项，以 `FilesPageReady` 返回 UI 主循环。
- Music 最多 128 首 WAV、播放控制、后台继续、1Hz 省电刷新和拔卡降级。
- Recorder 的 2MB 门槛、RTC/序号命名、`.tmp` 生命周期、可见录音状态和异常停止。
- Themes 最多 16 个主题、尺寸/字节数/图标包预算校验、具体错误明细、缓存回滚和完整控件树动态换肤。
- 计划 4A 识别的存储入口、失败传播、闹钟事件、后台分页和主题补全项均已写入代码。

### 7.2 尚未完成

- 媒体应用预览的最终集中视觉复核。
- 音乐、录音、主题三种状态各 10 次 SD 拔插。
- AudioProbe 短 PCM、2 秒录音和回放真机验证。
- 音乐、暂停、闹钟抢占和录音的 30 分钟及各 20 次循环。
- 四种铃声、音乐中抢占和屏幕关闭触发测试。
- Files 的 0、1、32、33、200 文件分页和扫描中拔卡测试。
- Music 30 分钟、100 次切歌和 10 次闹钟抢占。
- Recorder 5 秒、60 秒、10 分钟录音，以及拔卡和低电量中断。
- 有效/损坏/超限主题、拔卡和设置失败回滚的真实文件验证。
- 媒体期间触摸响应、堆低水位以及音频和 SD 空闲功耗。
- Task 4～11 与计划 4A 尚未提交。

结论：计划 4 已达到软件候选状态，视觉终验和完整真机矩阵仍未完成。

## 9. 当前不可破坏的边界

- LVGL 固定为 8.3.11，且只能由 Arduino UI 主循环访问。
- 后台任务只能采样、计算和投递固定容量事件。
- 共享 I2C 访问必须经过带超时的互斥边界。
- UI 适配 410 × 502 圆角安全区，主要触摸目标至少 48 × 48px。
- 正式 UI 修改先预览，再进行视觉复核和真机校准。
- 列表、队列、导航、缓存和媒体索引使用固定容量。
- 无手机、无网络、无 SD 或部分硬件失败时，核心系统应保持独立运行和明确降级。
- 不删除或覆盖 `image\图片生成提示词`。
- 未执行的真机项目不得标记为通过。

## 10. 建议收口顺序

1. 集中展示计划 4 媒体应用预览并记录视觉终验结果。
2. 连接开发板，依次完成计划 1 Gate A、计划 2 Gate B、计划 3 电源/IMU 矩阵和计划 4 存储/音频/媒体矩阵。
3. 将真机次数、失败现象、内存低水位、转场耗时和功耗数据写回对应模块说明与验收记录。
4. 真机问题修复并重新验证稳定后，再按用户指令提交计划 4 Task 4～11 与 4A。
5. 未经明确指令不合并分支，不开始计划 5。
