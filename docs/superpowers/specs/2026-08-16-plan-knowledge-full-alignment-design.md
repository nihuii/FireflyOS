# FireflyOS 执行计划与知识库全量对齐设计

## 1. 目标

以当前 `main@fab5509` 和当前工作区源码为事实基线，按轻量知识库保存的模块边界、失败策略和渐进顺序，完整重写 `docs/执行计划/` 中现有九份计划文档。

重写后必须让下一轮开发者能够明确回答：

- 当前 main 已经具备什么；
- 哪些只是主程序级能力、UI 路由、能力枚举或分区预留；
- 哪些独立服务仍需从当前 main 增量开发；
- 每项功能依赖哪张知识库卡片、应按什么顺序实现、如何自动验证和真机验收；
- 哪些历史源码只能作为本地对象参考，不能批量恢复或直接合并。

## 2. 权威顺序

发生冲突时按以下顺序判断：

1. 当前工作区源码、构建配置和实时 Git 证据决定“当前已有能力”。
2. `docs/项目介绍-对话衔接版.md` 汇总当前基线、约束和已知问题。
3. `knowledge/` 提供设计边界、风险、最小实现和复用顺序。
4. `docs/执行计划/` 只定义后续实施步骤和验收门槛，不反向证明功能已存在。
5. 本地历史 Git 对象只提供人工移植参考，不是当前源码或可直接合并的分支。

## 4. 统一状态模型

所有计划只使用以下状态：

| 状态 | 含义 |
|---|---|
| 当前已有 | 当前工作区存在可调用实现，但仍可能有缺陷或未完成真机验收 |
| 部分已有 | 只有主程序级装配、基础适配、UI 路由、能力枚举或配置基础 |
| 待开发 | 当前工作区不存在目标服务或完整业务闭环 |
| 待真机 | 软件证据存在，但硬件操作、稳定性、功耗或互操作尚未重新验证 |
| 阻塞 | 缺少必须的硬件证据、外部生产材料或用户授权，不能安全进入下一步 |

禁止把 UI 占位、核心枚举、分区布局、历史对象、编译成功或自动测试通过写成完整功能或真机通过。

## 6. 当前能力边界

### 6.1 当前已有

- 核心事件、状态、生命周期、应用、资源和能力原语。
- I²C 管理、受锁寄存器访问和部分板级适配。
- UI Shell、固定深度导航、主题、组件、锁屏、桌面、系统面板和覆盖层。
- 电池/充电行为、RTC 读写、主程序级闹钟调度/UI/持久化。
- `Qmi8658ControlAdapter` 和相应测试、工具基础。
- 32MB 分区表中的 app0、app1、otadata、FFat 和 coredump 布局。

### 6.2 部分已有

- Activity、Weather、Music、Recorder、Files 只有 UI 路由或占位。
- 时间、闹钟、电源和 IMU 有主程序装配或基础适配，但没有完整独立服务闭环。
- 双应用分区具备 OTA 布局基础，但没有更新协调、签名清单或首启确认服务。
- TouchLib 仍直接访问 `Wire`，共享 I²C 所有权边界尚未完成。

### 6.3 待开发

- 统一存储与媒体服务、SD 受管入口、音频仲裁和完整媒体应用。
- BLE 协议、连接、配对、通知同步和 Android 工程。
- 按需 Wi-Fi、NTP、天气、临时大文件传输。
- OTA 状态机、签名验证、SD/HTTPS 来源、首启回滚。
- 有界诊断服务、恢复出厂流程和 Release 安全闭锁。

## 7. 重写后的阶段顺序

1. 冻结当前构建、核心边界和诊断基线，不重做已经存在的核心原语。
2. 修复系统面板完整手势接收，验证锁屏、桌面、下拉、上滑、BOOT 和息屏。
3. 将 Touch 纳入统一 I²C 所有权，再逐个接入 RTC、PMU 和 IMU 的后台行为。
4. 把主程序级时间、闹钟、电源和运动能力逐步收敛为独立服务。
5. 先建立 NVS、FFat 和 SD 受管入口，再加入主题、音频和媒体应用。
6. 从最小 BLE Hello、Pair、Ack 开始，再增加 Android、通知和设置同步。
7. 先 NTP，再配网和天气；网络功能使用显式高功耗租约。
8. 先临时文件传输，再签名 OTA、首启回滚、恢复出厂和 Release 闭锁。

任何阶段失败都回到最近的真机稳定点，不把补丁堆到后续总装层。

## 8. 各计划统一结构

除 00 总路线图外，计划 01～06 和补全计划采用以下章节：

1. 目标与当前状态。
2. 知识库依据。
3. 前置条件与禁止事项。
4. 功能范围与明确非目标。
5. 分任务实施顺序。
6. 自动验证。
7. 真机验收。
8. 退出门槛与下一计划。

任务必须使用复选框，给出准确文件范围、预期失败、最小实现、验证命令和预期结果。涉及 UI 的任务必须先预览；涉及硬件、无线、存储或音频的任务必须包含独立真机证据。

## 9. 关键冲突修正

- 将所有 `docs/项目介绍.md` 更新目标改为 `docs/项目介绍-对话衔接版.md`，或改为对应模块说明；不恢复已删除文件。

- 将 OTA 联合准入从计划 1 移回计划 6；计划 1 只保留通用资源治理能力。
- 将系统面板手势和 BOOT/息屏基线列为计划 2A 首要任务。
- 将 Touch 统一 I²C 所有权列为计划 3 的硬前置，完成前不启动后台 PMU/RTC/IMU 并发轮询。
- Android 路径只在计划 5 的“待创建文件”或历史参考中出现，不能描述为当前目录。
- 自动证据与真机证据分栏，所有正式硬件项从待真机开始。

## 10. 验证设计

### 10.1 结构验证

- 九份执行计划均存在且保留原文件名。
- 计划 01～06 和 01A、02A 都包含统一章节。
- 每张知识库卡片 01～13 在覆盖矩阵中恰有一个主要计划。

### 10.2 事实与禁用内容扫描

- 不出现旧工作树路径、旧功能分支、旧 main SHA 或 ahead 数量。
- 不再引用已删除的 `docs/项目介绍.md`。
- 不将 LittleFS 写成当前内部文件系统。
- 不把 Android、BLE、Wi-Fi、存储媒体、传输或 OTA 写成当前已实现。
- 不把 app0/app1 分区布局写成 OTA 服务已存在。

### 10.3 链接与知识库验证

- 执行 `python knowledge/validate_knowledge.py`，要求退出码为 0。
- 验证当前路径真实存在；未来创建路径必须明确标注“计划创建”。
- 历史对象路径必须明确标注“本地历史对象参考”。

### 10.4 Git 与作用域验证

- 执行 `git diff --check -- docs/执行计划 knowledge`。
- 审查 `git diff -- docs/执行计划 knowledge`，确认没有代码或受保护资源改动。
- 保持暂存区为空，不执行提交或推送。
- 交付时单独列出本任务修改与预先存在的用户变更；没有事前哈希时不声称既有脏文件获得字节级未变证明。

## 11. 完成标准

- 执行计划与知识库对当前能力、未来功能、依赖顺序和证据边界表述一致。
- 01～13 模块卡片全部映射到唯一主要执行计划，没有遗漏或重复归属。
- 当前首要任务明确为 UI 手势/硬件基线，其后才是 Touch/I²C 和计划 3～6。
- 计划保留足够的实现、测试和真机验收细节，但不包含失效的分支操作和历史完成结论。
- 所有自动验证通过；未执行的硬件项目继续标记为待真机。
