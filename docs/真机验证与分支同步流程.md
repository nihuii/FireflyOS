# FireflyOS 真机验证、问题修复与分支同步流程

本文档用于指导 FireflyOS 按开发时间顺序完成真机验证、问题修复、主线合并和下游分支同步。目标是让 `main` 始终只接收已经完成对应阶段真机验证或明确记录例外的内容，同时让后续计划分支及时吸收前序计划的修复。

| --- | --- | --- | --- | --- |

## 2. 基本原则

### 2.1 主线只接收已验证阶段

`main` 是项目主线。每个计划分支完成以下条件后，才合并到 `main`：

1. 自动验证通过，或已记录无法自动验证的合理原因。
2. 对应阶段的真机验证矩阵完成，或明确记录 `PENDING` / `FAIL` / 例外边界。
3. 验证中发现的问题已经修复、提交并复测。
4. 文档没有把“自动编译 / 单元测试通过”写成“真机通过”。
5. 当前 worktree 没有未提交改动。

### 2.2 修复放在“最早责任分支”

发现问题时，先判断问题属于哪个阶段：

| 问题归属 | 修复位置 |
| --- | --- |
| 计划 1 的核心架构、事件总线、HAL 抽象、生命周期、基础资源管理问题 | `codex/firefly-core` |
| 计划 2 的 LVGL UI Shell、导航、主题 token、组件样式问题 | `codex/ui-shell` |
| 计划 3 的时钟、设置、活动、IMU、电源、低功耗、手电、日历计算问题 | `codex/core-apps-power-imu` |
| 计划 4 的存储、SD、音频、音乐、录音、媒体应用问题 | `codex/storage-audio-media` |
| 计划 5 的 BLE 协议、配对、Android 伴侣、通知、手机同步问题 | `codex/ble-android` |

如果在验证后序分支时发现前序问题，不要直接在后序分支里“顺手改”。推荐流程是：

1. 暂停当前后序分支验证。
2. 切到最早责任分支修复。
3. 对该责任分支重新执行必要自动验证和真机复测。
4. 将责任分支合并进 `main`。
5. 将责任分支更新同步到它的下游分支。
6. 回到原来的后序分支继续验证。

这样可以避免同一个 bug 在多个计划分支里重复修复，也能保证 `main` 的历史是按计划层级逐步变好的。

### 2.3 下游分支用 merge 同步

这些分支已经推送到 GitHub。为了避免频繁改写远端历史，默认使用 `merge` 同步下游分支，不使用 `rebase`。

例如 `codex/firefly-core` 修复后，同步到 `codex/ui-shell`：

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS\.worktrees\ui-shell
git fetch origin
git merge origin/codex/firefly-core
git push
```

只有当你明确想重写分支历史、并能接受 `git push --force-with-lease` 时，才考虑 `rebase`。日常真机验证流程不建议使用。

## 3. 每轮验证前的准备

每次开始一个分支的真机验证前，先做这些检查。

### 3.1 更新远端信息

在主仓库目录执行：

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS
git fetch origin
```

### 3.2 确认所有 worktree 状态

```powershell
git -C .\.worktrees\firefly-core status --short --branch
git -C .\.worktrees\ui-shell status --short --branch
git -C .\.worktrees\core-apps-power-imu status --short --branch
git -C .\.worktrees\storage-audio-media status --short --branch
git -C .\.worktrees\ble-android status --short --branch
```

理想输出类似：

```text
## codex/ui-shell...origin/codex/ui-shell
```

如果出现 `M`、`A`、`D`、`??`，说明该 worktree 有未提交改动。开始真机验证前要先判断：

- 是上次未完成的修复：继续修复、测试、提交；
- 是临时文件或生成文件：确认 `.gitignore` 是否覆盖，不要误提交；
- 是不相关改动：不要混入本轮验证提交。

### 3.3 确认当前分支与远端同步

在准备验证的 worktree 中执行：

```powershell
git status --short --branch
git log --oneline --decorate -5
```

如果显示本地领先远端，先确认是否应该推送：

```powershell
git push
```

如果显示本地落后远端，先拉取远端更新。默认用 merge：

```powershell
git pull --ff-only
```

如果 `--ff-only` 失败，说明本地和远端各有提交，不要盲目处理；先查看：

```powershell
git log --oneline --graph --decorate --all -20
```

再决定是 merge、rebase，还是先备份本地改动。

## 4. 单个分支的标准验证流程

下面流程适用于每一个计划分支。

### 4.1 进入目标 worktree

以 `codex/ui-shell` 为例：

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS\.worktrees\ui-shell
git status --short --branch
```

确认当前分支正确：

```powershell
git branch --show-current
```

预期：

```text
codex/ui-shell
```

### 4.2 跑自动验证

自动验证只证明软件在测试和编译层面通过，不能替代真机验证。根据当前阶段选择命令。

通用 Python 契约测试：

```powershell
python -m unittest discover -s tests/python -v
```

固件编译建议使用项目已有脚本或 Arduino CLI 配置。若使用已有脚本，先查看脚本参数：

```powershell
Get-Help .\tools\build_firmware.ps1
```

计划 5 Android 伴侣应用需要额外验证：

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS\.worktrees\ble-android\AndroidCompanion
$env:JAVA_HOME='C:\APP\Android\Android Studio\jbr'
$env:Path="$env:JAVA_HOME\bin;$env:Path"
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug --no-daemon --console=plain
```

生成 Debug APK 后记录 SHA-256：

```powershell
Get-FileHash .\app\build\outputs\apk\debug\app-debug.apk -Algorithm SHA256
```

文档中必须写成“Debug APK 编译成功 / Android 单元测试通过”，不能写成“Android 真机通过”。

### 4.3 执行真机验证

每个阶段至少记录：

| 字段 | 内容 |
| --- | --- |
| 分支 | 例如 `codex/ui-shell` |
| 提交 | `git rev-parse --short HEAD` |
| 固件构建产物 | 编译时间、Flash/RAM 占用、分区表 |
| 开发板 | 型号、屏幕、IMU、SD 卡、扬声器/麦克风等硬件配置 |
| Android 手机 | 仅计划 5 需要；记录品牌、型号、Android 版本、BLE 权限状态 |
| 测试日期 | 使用绝对日期，例如 `2026-07-30` |
| 测试人 | 手动记录 |
| 日志 | 串口日志、截图、视频、APK SHA-256 |
| 结果 | `PASS-HW` / `PENDING` / `FAIL` |

建议把结果记录在对应模块说明或执行计划文档里。没有实际证据时保持 `PENDING`，不要提前写 `PASS-HW`。

## 5. 问题发现后的修复流程

### 5.1 记录问题

先不要急着改代码。建议先记下：

```text
问题编号：
发现分支：
发现提交：
真机环境：
复现步骤：
预期结果：
实际结果：
日志/截图/视频：
初步归属阶段：
```

### 5.2 判断责任分支

用“最早责任分支”规则判断修复位置。

例 1：验证 `codex/ui-shell` 时发现 LVGL 导航栈返回异常。  
责任分支是 `codex/ui-shell`，直接在 `ui-shell` worktree 修。

例 2：验证 `codex/storage-audio-media` 时发现低功耗唤醒后 I2C 资源状态错误。  
如果该问题来自计划 3 的电源/IMU 生命周期，应回到 `codex/core-apps-power-imu` 修，再向后同步。

例 3：验证 `codex/ble-android` 时发现 Android 权限弹窗流程异常。  
责任分支是 `codex/ble-android`，不要回写到前序分支。

### 5.3 在责任分支修复

以 `codex/core-apps-power-imu` 为例：

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS\.worktrees\core-apps-power-imu
git status --short --branch
```

修改代码前，确认没有不相关未提交改动。

修复后先跑针对性验证：

```powershell
python -m unittest discover -s tests/python -v
```

再执行与问题直接相关的真机复测。

### 5.4 提交修复

```powershell
git status --short
git diff --check
git add <修复文件> <测试文件> <文档文件>
git commit -m "fix: describe the hardware validation issue"
git push
```

提交信息建议保持简短明确：

| 类型 | 示例 |
| --- | --- |
| 修复真机问题 | `fix: stabilize imu wake recovery` |
| 补充验收记录 | `docs: record plan 3 hardware validation` |
| 测试补充 | `test: cover power wake recovery contract` |

## 6. 合并到 main 的流程

当当前计划分支通过本阶段验收后，把它合并到 `main`。

以下以 `codex/ui-shell` 为例。

### 6.1 先确认计划分支干净且已推送

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS\.worktrees\ui-shell
git status --short --branch
git push
```

如果 `git push` 输出 `Everything up-to-date`，说明远端已经有最新提交。

### 6.2 回到主线 worktree

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS
git status --short --branch
git fetch origin
git pull --ff-only
```

如果主线有未提交改动，不要合并；先处理主线工作区。

### 6.3 合并计划分支

推荐使用 `--no-ff`，这样主线历史能清楚显示“某个计划分支在这里被合入”：

```powershell
git merge --no-ff origin/codex/ui-shell -m "merge: validate ui shell into main"
```

如果有冲突：

1. 阅读冲突文件，优先保留已通过真机验证的当前计划分支行为。
2. 不确定时停止，不要凭感觉覆盖。
3. 解决冲突后运行自动验证和必要的真机冒烟复测。
4. 再完成 merge commit：

```powershell
git add <冲突文件>
git commit
```

### 6.4 推送 main

```powershell
git push origin main
```

推送后确认：

```powershell
git log --oneline --decorate -5
git branch -r --contains HEAD
```

## 7. 同步到下游分支的流程

当前计划分支合并到 `main` 后，还要把该计划分支的最新修复同步到下游分支。同步源使用“当前刚验证通过的计划分支”，不是随手用任意分支。

### 7.1 同步关系表

## 9. 冲突处理规则

### 9.1 遇到 merge conflict 时

Git 会提示类似：

```text
CONFLICT (content): Merge conflict in <file>
Automatic merge failed; fix conflicts and then commit the result.
```

处理步骤：

```powershell
git status --short
```

打开冲突文件，查找：

```text
<<<<<<<
=======
>>>>>>>
```

手动整理成最终正确内容后：

```powershell
git diff --check
git add <冲突文件>
git commit
git push
```

### 9.2 不确定时不要强行解决

以下情况应暂停：

- 冲突涉及 LVGL 主循环访问边界；
- 冲突涉及固定容量队列、NVS 存储格式、分区表；
- 冲突涉及 BLE 协议帧、配对 token、HMAC、ACK、解绑事务；
- 冲突涉及已经真机通过的行为；
- 冲突看起来需要删除或覆盖 `image\图片生成提示词`。

暂停后先记录冲突文件、两个版本的差异和你的倾向，再决定处理方案。

## 10. 禁止事项

1. 不要把自动编译、Python 测试或 Android JVM 单元测试写成真机通过。
2. 不要在 Gate D 未执行时把 D-01～D-12 改成 `PASS-HW`。
3. 不要跳过上游分支，直接把后序分支合并进 `main`。
4. 不要在后序分支里修前序分支的根因问题后直接继续；应回到最早责任分支修复并向后同步。
5. 不要用 `git reset --hard`、强制删除、覆盖用户资料等破坏性操作清理问题。
6. 不要删除或覆盖 `image\图片生成提示词`。
7. 不要在计划 5 完成前创建、提交或推进计划 6。

## 12. 快速命令索引

查看分支链：

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS
git log --graph --oneline --decorate --all --max-count=80
```

查看 worktree：

```powershell
git worktree list
```

查看本地和远端分支：

```powershell
git branch -vv
git branch -r
```

查看某分支是否已合入 main：

```powershell
git branch --merged main
```

查看某分支相对 main 的领先/落后：

```powershell
git rev-list --left-right --count main...codex/ui-shell
```

把当前分支推送到远端：

```powershell
git push
```

把当前计划分支合入 main：

```powershell
cd D:\Study\Projects\ESP32Projects\FireflyOS
git fetch origin
git pull --ff-only
git merge --no-ff origin/<计划分支名> -m "merge: validate <计划名> into main"
git push origin main
```

把上游计划分支同步到下游计划分支：

```powershell
cd <下游 worktree>
git fetch origin
git merge origin/<上游计划分支名>
git push
```
